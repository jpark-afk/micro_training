\doxysubsubsection{Detailed Description}
{\itshape \doxylink{group__DDSDocGuideModule_a_st_cert}{\texorpdfstring{$<$}{<}\texorpdfstring{$<$}{<}cert\texorpdfstring{$>$}{>}\texorpdfstring{$>$}{>}}}  Determines the mechanism and parameters used by the application to determine whether a \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} is alive. 

Liveliness must be asserted at least once every {\ttfamily lease\+\_\+duration} otherwise RTI Connext DDS Micro will assume the corresponding \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} or is no longer alive. 

The liveliness status of a \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} is used to maintain instance ownership in combination with the setting of the \doxylink{group__DDSOwnershipQosModule}{OWNERSHIP} policy. The application is also informed via \doxylink{structDDS__Listener}{DDS\+\_\+\+Listener} when an \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} is no longer alive. 

A \doxylink{group__DDSReaderModule_ga49ce0cab2c1b60ddee4784a1432577a4}{DDS\+\_\+\+Data\+Reader} requests that liveliness of writers is maintained by the requested means and loss of liveliness is detected with delay not to exceed the {\ttfamily lease\+\_\+duration}. 

A \doxylink{group__DDSWriterModule_gafb74fa54675abe1bfb2090265bf4d116}{DDS\+\_\+\+Data\+Writer} commits to signalling its liveliness using the stated means at intervals not to exceed the {\ttfamily lease\+\_\+duration}. 

Listeners are used to notify a \doxylink{group__DDSReaderModule_ga49ce0cab2c1b60ddee4784a1432577a4}{DDS\+\_\+\+Data\+Reader} of loss of liveliness and \doxylink{group__DDSWriterModule_gafb74fa54675abe1bfb2090265bf4d116}{DDS\+\_\+\+Data\+Writer} of violations to the liveliness contract. The on\+\_\+liveliness\+\_\+lost() callback is only called {\itshape once}, after the first time the {\ttfamily lease\+\_\+duration} is exceeded (when the \doxylink{group__DDSWriterModule_gafb74fa54675abe1bfb2090265bf4d116}{DDS\+\_\+\+Data\+Writer} first loses liveliness). 

This QoS policy can be used during system integration to ensure that applications have been coded to meet design specifications. It can also be used during run time to detect when systems are performing outside of design specifications. Receiving applications can take appropriate actions in response to disconnected Data\+Writers.

\hypertarget{structDDS__LivelinessQosPolicy_DDSLivelinessQosModule_usage}{}\doxysubsubsection{\texorpdfstring{Usage}{Usage}}\label{structDDS__LivelinessQosPolicy_DDSLivelinessQosModule_usage}
This policy controls the mechanism and parameters used by RTI Connext DDS Micro to ensure that particular entities on the network are still alive. The liveliness can also affect the ownership of a particular instance, as determined by the \doxylink{group__DDSOwnershipQosModule}{OWNERSHIP} policy. 

This policy has several settings to support both data types that are updated periodically as well as those that are changed sporadically. It also allows customisation for different application requirements in terms of the kinds of failures that will be detected by the liveliness mechanism. 

The \doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5ad9cee7b01dd754152a13b6999b57911b}{DDS\+\_\+\+AUTOMATIC\+\_\+\+LIVELINESS\+\_\+\+QOS} liveliness setting is most appropriate for applications that only need to detect failures at the process-\/level, but not application-\/logic failures within a process. RTI Connext DDS Micro takes responsibility for renewing the leases at the required rates and thus, as long as the local process where a \doxylink{group__DDSDomainParticipantModule_ga1964274885335d5bcea6855f66b0bfe1}{DDS\+\_\+\+Domain\+Participant} is running and the link connecting it to remote participants remains connected, the entities within the \doxylink{group__DDSDomainParticipantModule_ga1964274885335d5bcea6855f66b0bfe1}{DDS\+\_\+\+Domain\+Participant} will be considered alive. This requires the lowest overhead. 

The manual settings (\doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5a5519eb00b713987173ff0858e7e3c1f0}{DDS\+\_\+\+MANUAL\+\_\+\+BY\+\_\+\+PARTICIPANT\+\_\+\+LIVELINESS\+\_\+\+QOS}, \doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5a6ea670a089709fe482e1c92f5ad1c255}{DDS\+\_\+\+MANUAL\+\_\+\+BY\+\_\+\+TOPIC\+\_\+\+LIVELINESS\+\_\+\+QOS}) require the application on the publishing side to periodically assert the liveliness before the lease expires to indicate the corresponding \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} is still alive. The action can be explicit by calling the \doxylink{group__DDSWriterModule_ga0427bb22acd04dce70e69dd731bc74ba}{DDS\+\_\+\+Data\+Writer\+\_\+assert\+\_\+liveliness} operation or implicit by writing some data. 

The two possible manual settings control the granularity at which the application must assert liveliness. 

\begin{DoxyItemize}
\item The setting \doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5a5519eb00b713987173ff0858e7e3c1f0}{DDS\+\_\+\+MANUAL\+\_\+\+BY\+\_\+\+PARTICIPANT\+\_\+\+LIVELINESS\+\_\+\+QOS} requires only that one \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} within a participant is asserted to be alive to deduce all other \doxylink{group__DDSEntityModule_ga928b59d917d674720975f0581149b905}{DDS\+\_\+\+Entity} objects within the same \doxylink{group__DDSDomainParticipantModule_ga1964274885335d5bcea6855f66b0bfe1}{DDS\+\_\+\+Domain\+Participant} are also alive. \end{DoxyItemize}
\begin{DoxyItemize}
\item The setting \doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5a6ea670a089709fe482e1c92f5ad1c255}{DDS\+\_\+\+MANUAL\+\_\+\+BY\+\_\+\+TOPIC\+\_\+\+LIVELINESS\+\_\+\+QOS} requires that at least one instance within the \doxylink{group__DDSWriterModule_gafb74fa54675abe1bfb2090265bf4d116}{DDS\+\_\+\+Data\+Writer} is asserted. \end{DoxyItemize}
