The exact behavior of this may be OS dependent. In some OSs calling this will immediately cause the semaphore to be removed, and other threads waiting on it to be woken up. This is the typical behavior on Unix. In other OSs (windows) this call just requests the semaphore to be removed but delay the removal until all handles are detached.

The only way to ensure the same behavior across multiple OSs is to only call this method on the handle that created the semaphore after all the other handles have been closed. In this scenario no handles will get an error. Alternatively the code could be written to always expect the \doxylink{group__NETIO__SharedMemorySignalingSemaphoreClass_ga2dda7edf9e1f39ca68510a3c52429d26}{NETIO\+\_\+\+Shared\+Memory\+Signaling\+Semaphore\+\_\+wait} or \doxylink{group__NETIO__SharedMemorySignalingSemaphoreClass_gae5cd64e1136b34eb62da0f9348d4ae57}{NETIO\+\_\+\+Shared\+Memory\+Signaling\+Semaphore\+\_\+signal} call to fail and when that occurs close the handle.

Handle in the ATTACHED state.
