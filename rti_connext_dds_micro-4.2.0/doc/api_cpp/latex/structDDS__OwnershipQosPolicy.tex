\hypertarget{structDDS__OwnershipQosPolicy_DDSOwnershipQosModule_usage}{}\doxysubsubsection{\texorpdfstring{Usage}{Usage}}\label{structDDS__OwnershipQosPolicy_DDSOwnershipQosModule_usage}
This policy controls whether RTI Connext DDS Micro allows multiple \doxylink{classDDSDataWriter}{DDSData\+Writer} objects to update the same instance (identified by \doxylink{classDDSTopic}{DDSTopic} + key) of a data type. 

There are two kinds of owner selected by the setting of the {\ttfamily kind\+:} SHARED and EXCLUSIVE. \hypertarget{dds_c_infrastructure.h_DDSOwnershipQosModule_usage_shared}{}\doxysubsubsubsection{\texorpdfstring{SHARED ownership}{SHARED ownership}}\label{dds_c_infrastructure.h_DDSOwnershipQosModule_usage_shared}
\doxylink{group__DDSOwnershipQosModule_ggaa88100c64a26cc036cb2eb2d631c3f43a262c9859d5c214495c02cd39366a335f}{DDS\+\_\+\+SHARED\+\_\+\+OWNERSHIP\+\_\+\+QOS} indicates that RTI Connext DDS Micro does not enforce unique ownership for each instance. In this case, multiple writers can update the same data type instance. The subscriber to the \doxylink{classDDSTopic}{DDSTopic} will be able to access modifications from all \doxylink{classDDSDataWriter}{DDSData\+Writer} objects, subject to the settings of other QoS that may filter particular samples (e.\+g. the \doxylink{group__DDSHistoryQosModule}{HISTORY} policy). In any case there is no "{}filtering"{} of modifications made based on the identity of the \doxylink{classDDSDataWriter}{DDSData\+Writer} that causes the modification. \hypertarget{dds_c_infrastructure.h_DDSOwnershipQosModule_usage_exclusive}{}\doxysubsubsubsection{\texorpdfstring{EXCLUSIVE ownership}{EXCLUSIVE ownership}}\label{dds_c_infrastructure.h_DDSOwnershipQosModule_usage_exclusive}
\doxylink{group__DDSOwnershipQosModule_ggaa88100c64a26cc036cb2eb2d631c3f43a6f223289a81f87d7929408a84a27f316}{DDS\+\_\+\+EXCLUSIVE\+\_\+\+OWNERSHIP\+\_\+\+QOS} indicates that each instance of a data type can only be modified by one \doxylink{classDDSDataWriter}{DDSData\+Writer}. In other words, at any point in time a single \doxylink{classDDSDataWriter}{DDSData\+Writer} owns each instance and is the only one whose modifications will be visible to the \doxylink{classDDSDataReader}{DDSData\+Reader} objects. The owner is determined by selecting the \doxylink{classDDSDataWriter}{DDSData\+Writer} with the highest value of the \doxylink{structDDS__OwnershipStrengthQosPolicy_afda6a59cd3cfd9bc904c98efc68a61eb}{DDS\+\_\+\+Ownership\+Strength\+Qos\+Policy\+::value} that is currently alive as defined by the \doxylink{group__DDSLivelinessQosModule}{LIVELINESS} policy and has not violated its \doxylink{group__DDSDeadlineQosModule}{DEADLINE} contract with regards to the data-\/instance. 

Ownership can therefore change as a result of\+: 

\begin{DoxyItemize}
\item a \doxylink{classDDSDataWriter}{DDSData\+Writer} in the system with a higher value of the strength that modifies the instance,  \item a change in the strength value of the \doxylink{classDDSDataWriter}{DDSData\+Writer} that owns the instance, and  \item a change in the liveliness of the \doxylink{classDDSDataWriter}{DDSData\+Writer} that owns the instance. \item a deadline with regards to the instance that is missed by the \doxylink{classDDSDataWriter}{DDSData\+Writer} that owns the instance. \end{DoxyItemize}
The behavior of the system is as if the determination was made independently by each \doxylink{classDDSDataReader}{DDSData\+Reader}. Each \doxylink{classDDSDataReader}{DDSData\+Reader} may detect the change of ownership at a different time. It is not a requirement that at a particular point in time all the \doxylink{classDDSDataReader}{DDSData\+Reader} objects for that \doxylink{classDDSTopic}{DDSTopic} have a consistent picture of who owns each instance. 

It is also not a requirement that the \doxylink{classDDSDataWriter}{DDSData\+Writer} objects are aware of whether they own a particular instance. There is no error or notification given to a \doxylink{classDDSDataWriter}{DDSData\+Writer} that modifies an instance it does not currently own. 

The requirements are chosen to (a) preserve the decoupling of publishers and subscribers, and (b) allow the policy to be implemented efficiently. 

It is possible that multiple \doxylink{classDDSDataWriter}{DDSData\+Writer} objects with the same strength modify the same instance. If this occurs RTI Connext DDS Micro will pick one of the \doxylink{classDDSDataWriter}{DDSData\+Writer} objects as the owner. It is not specified how the owner is selected. However, it is required that the policy used to select the owner is such that all \doxylink{classDDSDataReader}{DDSData\+Reader} objects will make the same choice of the particular \doxylink{classDDSDataWriter}{DDSData\+Writer} that is the owner. It is required that the owner remains the same until there is a change in strength, liveliness, the owner misses a deadline on the instance, or a new \doxylink{classDDSDataWriter}{DDSData\+Writer} with higher same strength, or a new \doxylink{classDDSDataWriter}{DDSData\+Writer} with same strength that should be deemed the owner according to the policy of the Service, modifies the instance. 

Exclusive ownership is on an instance-\/by-\/instance basis. That is, a subscriber can receive values written by a lower strength \doxylink{classDDSDataWriter}{DDSData\+Writer} as long as they affect instances whose values have not been set by the higher-\/strength \doxylink{classDDSDataWriter}{DDSData\+Writer}. \hypertarget{dds_c_infrastructure.h_DDSOwnershipQosModule_compatibility}{}\doxysubsubsection{\texorpdfstring{Compatibility}{Compatibility}}\label{dds_c_infrastructure.h_DDSOwnershipQosModule_compatibility}
The value of the \doxylink{group__DDSOwnershipQosModule_gaa88100c64a26cc036cb2eb2d631c3f43}{DDS\+\_\+\+Ownership\+Qos\+Policy\+Kind} offered must exactly match the one requested or else they are considered incompatible. \hypertarget{dds_c_infrastructure.h_Ownership_redundant_systems}{}\doxysubsubsubsection{\texorpdfstring{Ownership Resolution on Redundant Systems}{Ownership Resolution on Redundant Systems}}\label{dds_c_infrastructure.h_Ownership_redundant_systems}
It is expected that users may use DDS to set up redundant systems where multiple \doxylink{classDDSDataWriter}{DDSData\+Writer} entities are "{}capable"{} of writing the same instance. In this situation, the \doxylink{classDDSDataWriter}{DDSData\+Writer} entities are configured such that\+: 

\begin{DoxyItemize}
\item Either both are writing the instance "{}constantly"{} \end{DoxyItemize}
\begin{DoxyItemize}
\item Or else they use some mechanism to classify each other as "{}primary"{} and "{}secondary"{}, such that the primary is the only one writing, and the secondary monitors the primary and only writes when it detects that the primary "{}writer"{} is no longer writing. \end{DoxyItemize}
Both cases above use the \doxylink{group__DDSOwnershipQosModule_ggaa88100c64a26cc036cb2eb2d631c3f43a6f223289a81f87d7929408a84a27f316}{DDS\+\_\+\+EXCLUSIVE\+\_\+\+OWNERSHIP\+\_\+\+QOS} and arbitrate themselves by means of the \doxylink{structDDS__OwnershipStrengthQosPolicy}{DDS\+\_\+\+Ownership\+Strength\+Qos\+Policy}. Regardless of the scheme, the desired behavior from the \doxylink{classDDSDataReader}{DDSData\+Reader} point of view is that \doxylink{classDDSDataReader}{DDSData\+Reader} normally receives data from the primary unless the "{}primary"{} writer stops writing, in which case the \doxylink{classDDSDataReader}{DDSData\+Reader} starts to receive data from the secondary \doxylink{classDDSDataWriter}{DDSData\+Writer}. 

This approach requires some mechanism to detect that a \doxylink{classDDSDataWriter}{DDSData\+Writer} (the primary) is no longer "{}writing"{} the data as it should. There are several reasons why this may happen and all must be detected (but not necessarily distinguished)\+: 

\begin{DoxyItemize}
\item \mbox{[}crash\mbox{]} The writing process is no longer running (e.\+g. the whole application has crashed) \end{DoxyItemize}
\begin{DoxyItemize}
\item \mbox{[}connectivity loss\mbox{]} Connectivity to the writing application has been lost (e.\+g. network disconnection) \end{DoxyItemize}
\begin{DoxyItemize}
\item \mbox{[}application fault\mbox{]} The application logic that was writing the data is faulty and has stopped calling \doxylink{structFooDataWriter_ab2c44dd15f5daf7eddf3773239101478}{Foo\+Data\+Writer\+::write}. \end{DoxyItemize}
Arbitrating from a \doxylink{classDDSDataWriter}{DDSData\+Writer} to one of a higher strength is simple and the decision can be taken autonomously by the \doxylink{classDDSDataReader}{DDSData\+Reader}. Switching ownership from a higher strength \doxylink{classDDSDataWriter}{DDSData\+Writer} to one of a lower strength \doxylink{classDDSDataWriter}{DDSData\+Writer} requires that the \doxylink{classDDSDataReader}{DDSData\+Reader} can make a determination that the stronger \doxylink{classDDSDataWriter}{DDSData\+Writer} is "{}no longer writing the instance"{}. \hypertarget{dds_c_infrastructure.h_Ownership_data_periodic_update}{}\doxysubsubsubsubsection{\texorpdfstring{Case where the data is periodically updated}{Case where the data is periodically updated}}\label{dds_c_infrastructure.h_Ownership_data_periodic_update}
This determination is reasonably simple when the data is being written periodically at some rate. The \doxylink{classDDSDataWriter}{DDSData\+Writer} simply states its offered \doxylink{structDDS__DeadlineQosPolicy}{DDS\+\_\+\+Deadline\+Qos\+Policy} (maximum interval between updates) and the \doxylink{classDDSDataReader}{DDSData\+Reader} automatically monitors that the \doxylink{classDDSDataWriter}{DDSData\+Writer} indeed updates the instance at least once per \doxylink{structDDS__DeadlineQosPolicy_a3bc084edc8320df0e64d8ac2b857635d}{DDS\+\_\+\+Deadline\+Qos\+Policy\+::period}. If the deadline is missed, the \doxylink{classDDSDataReader}{DDSData\+Reader} considers the \doxylink{classDDSDataWriter}{DDSData\+Writer} "{}not alive"{} and automatically gives ownership to the next highest-\/strength \doxylink{classDDSDataWriter}{DDSData\+Writer} that {\itshape is} alive. \hypertarget{dds_c_infrastructure.h_Ownership_data_not_periodic_update}{}\doxysubsubsubsubsection{\texorpdfstring{Case where data is not periodically updated}{Case where data is not periodically updated}}\label{dds_c_infrastructure.h_Ownership_data_not_periodic_update}
The case where the \doxylink{classDDSDataWriter}{DDSData\+Writer} is not writing data periodically is also a very important use-\/case. Since the instance is not being updated at any fixed period, the "{}deadline"{} mechanism cannot be used to determine ownership. The liveliness solves this situation. Ownership is maintained while the \doxylink{classDDSDataWriter}{DDSData\+Writer} is "{}alive"{} and for the \doxylink{classDDSDataWriter}{DDSData\+Writer} to be alive it must fulfill its \doxylink{structDDS__LivelinessQosPolicy}{DDS\+\_\+\+Liveliness\+Qos\+Policy} contract. The different means to renew liveliness (automatic, manual) combined by the implied renewal each time data is written handle the three conditions above \mbox{[}crash\mbox{]}, \mbox{[}connectivity loss\mbox{]}, and \mbox{[}application fault\mbox{]}. Note that to handle \mbox{[}application fault\mbox{]}, LIVELINESS must be \doxylink{group__DDSLivelinessQosModule_gga3ea638553fd66356c38071040de062e5a6ea670a089709fe482e1c92f5ad1c255}{DDS\+\_\+\+MANUAL\+\_\+\+BY\+\_\+\+TOPIC\+\_\+\+LIVELINESS\+\_\+\+QOS}. The \doxylink{classDDSDataWriter}{DDSData\+Writer} can retain ownership by periodically writing data or else calling assert\+\_\+liveliness if it has no data to write. Alternatively if only protection against \mbox{[}crash\mbox{]} or \mbox{[}connectivity loss\mbox{]} is desired, it is sufficient that some task on the \doxylink{classDDSDataWriter}{DDSData\+Writer} process periodically writes data. However, this scenario requires that the \doxylink{classDDSDataReader}{DDSData\+Reader} knows what instances are being "{}written"{} by the \doxylink{classDDSDataWriter}{DDSData\+Writer}. That is the only way that the \doxylink{classDDSDataReader}{DDSData\+Reader} deduces the ownership of specific instances from the fact that the \doxylink{classDDSDataWriter}{DDSData\+Writer} is still "{}alive"{}. \hypertarget{dds_c_infrastructure.h_Ownership_loss_connectivity_detection}{}\doxysubsubsubsection{\texorpdfstring{Detection of Loss in Topological Connectivity}{Detection of Loss in Topological Connectivity}}\label{dds_c_infrastructure.h_Ownership_loss_connectivity_detection}
There are applications that are designed in such a way that their correct operation requires some minimal topological connectivity, that is, the writer needs to have a minimum number of readers or alternatively the reader must have a minimum number of writers. 

A common scenario is that the application does not start doing its logic until it knows that some specific writers have the minimum configured readers (e.\+g the alarm monitor is up). 

A {\itshape more} common scenario is that the application logic will wait until some writers appear that can provide some needed source of information (e.\+g. the raw sensor data that must be processed). 

Furthermore, once the application is running it is a requirement that this minimal connectivity (from the source of the data) is monitored and the application informed if it is ever lost. For the case where data is being written periodically, the \doxylink{structDDS__DeadlineQosPolicy}{DDS\+\_\+\+Deadline\+Qos\+Policy} and the on\+\_\+deadline\+\_\+missed listener provides the notification. The case where data is not periodically updated requires the use of the \doxylink{structDDS__LivelinessQosPolicy}{DDS\+\_\+\+Liveliness\+Qos\+Policy} to detect whether the "{}connectivity"{} has been lost, and the notification is provided by means of \doxylink{group__DDSInstanceStateModule_ggaf2264cae1aa8cd66490debfdc5e0c360a72ebdc6f53c9a7588458b48e3ea66507}{DDS\+\_\+\+NOT\+\_\+\+ALIVE\+\_\+\+NO\+\_\+\+WRITERS\+\_\+\+INSTANCE\+\_\+\+STATE}. 

In terms of the required mechanisms, the scenario is very similar to the case of maintaining ownership. In both cases, the reader needs to know whether a writer is still "{}managing the current value of an instance"{} even though it is not continually writing it and this knowledge requires the writer to keep its liveliness. 

For a \doxylink{classDDSTopic}{DDSTopic} with \doxylink{group__DDSOwnershipQosModule_ggaa88100c64a26cc036cb2eb2d631c3f43a6f223289a81f87d7929408a84a27f316}{DDS\+\_\+\+EXCLUSIVE\+\_\+\+OWNERSHIP\+\_\+\+QOS}, if the current owner of an instance {\itshape disposes} it, the readers accessing the instance will see the instance\+\_\+state as being "{}DISPOSED"{} and not see the values being written by the weaker writer (even after the stronger one has disposed the instance). This is because the \doxylink{classDDSDataWriter}{DDSData\+Writer} that owns the instance is saying that the instance no longer exists (e.\+g. the master of the database is saying that a record has been deleted) and thus the readers should see it as such.
