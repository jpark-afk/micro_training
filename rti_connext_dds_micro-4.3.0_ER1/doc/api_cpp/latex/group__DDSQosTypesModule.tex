\doxysubsubsubsubsection{Detailed Description}
Quality of Service (QoS) policies. 

Data Distribution Service (DDS) relies on the use of QoS. A QoS is a set of characteristics that controls some aspect of the behavior of DDS. A QoS is comprised of individual QoS policies (objects conceptually deriving from an {\itshape abstract} {\ttfamily Qos\+Policy} class). 

RTI Connext DDS Micro supports a subset of these QoS. 

 

The Qos\+Policy provides the basic mechanism for an application to specify quality of service parameters. A Qos\+Policy may have additional properties associated with it\+: 


\begin{DoxyItemize}
\item {\bfseries{\doxylink{group__DDSQosTypesModule_a_prop_rxo}{RxO}\label{group__DDSQosTypesModule_a_prop_rxo}%
\Hypertarget{group__DDSQosTypesModule_a_prop_rxo}%
 property}}~\newline
 The Qos\+Policy objects that need to be set in a compatible manner between the {\bfseries{publisher}} and {\bfseries{subscriber}} end are indicated by the setting of the \doxylink{group__DDSQosTypesModule_a_prop_rxo}{RxO} property\+:  
\begin{DoxyItemize}
\item \doxylink{group__DDSQosTypesModule_a_prop_rxo}{RxO} = {\bfseries{YES}}  indicates that the policy can be set both at the publishing and subscribing ends and the values must be set in a compatible manner. In this case the compatible values are explicitly defined.  
\item \doxylink{group__DDSQosTypesModule_a_prop_rxo}{RxO} = {\bfseries{NO}}  indicates that the policy can be set both at the publishing and subscribing ends but the two settings are independent. That is, all combinations of values are compatible. 
\item \doxylink{group__DDSQosTypesModule_a_prop_rxo}{RxO} = {\bfseries{N/A}}  indicates that the policy can only be specified at either the publishing or the subscribing end, but not at both ends. So compatibility does not apply. 
\end{DoxyItemize}
\item {\bfseries{\doxylink{group__DDSQosTypesModule_a_prop_changeable}{Changeable}\label{group__DDSQosTypesModule_a_prop_changeable}%
\Hypertarget{group__DDSQosTypesModule_a_prop_changeable}%
 property}}~\newline
 Determines whether a Qos\+Policy can be changed. ~\newline
{\bfseries{\doxylink{group__DDSQosTypesModule_a_prop_changeable_no}{NO}\label{group__DDSQosTypesModule_a_prop_changeable_no}%
\Hypertarget{group__DDSQosTypesModule_a_prop_changeable_no}%

{\bfseries{\doxylink{group__DDSQosTypesModule_a_prop_changeable_until_enable}{UNTIL ENABLE}\label{group__DDSQosTypesModule_a_prop_changeable_until_enable}%
\Hypertarget{group__DDSQosTypesModule_a_prop_changeable_until_enable}%

Qos\+Policy implementation is comprised of a name, an ID, and a type. The type of a {\ttfamily Qos\+Policy} value may be atomic, such as an integer or float, or compound structures. Compound types are used whenever multiple parameters must be set coherently to define a consistent value for a Qos\+Policy. 

QoS, which is a list of {\ttfamily Qos\+Policy} objects, may be associated with all \doxylink{classDDSEntity}{DDSEntity} objects in the system such as \doxylink{classDDSTopic}{DDSTopic}, \doxylink{classDDSDataWriter}{DDSData\+Writer}, \doxylink{classDDSDataReader}{DDSData\+Reader}, \doxylink{classDDSPublisher}{DDSPublisher}, \doxylink{classDDSSubscriber}{DDSSubscriber}, and \doxylink{classDDSDomainParticipant}{DDSDomain\+Participant}. \hypertarget{group__DDSQosTypesModule_DDSQosTypesModule_usage}{}\doxysubsubsubsubsection{\texorpdfstring{Specifying QoS on entities}{Specifying QoS on entities}}\label{group__DDSQosTypesModule_DDSQosTypesModule_usage}
Qos\+Policies can be set programmatically when an \doxylink{classDDSEntity}{DDSEntity} is created, or modified with the \doxylink{classDDSEntity}{DDSEntity}\textquotesingle{}s \doxysectlink{dds_cpp_infrastructure.hxx_Entity_set_qos}{set\+\_\+qos (abstract)}{2} method. 

To customize a \doxylink{classDDSEntity}{DDSEntity}\textquotesingle{}s QoS before creating the entity, the correct pattern is\+: 

\begin{DoxyItemize}
\item First, initialize a QoS object with the appropriate INITIALIZER  constructor.  \end{DoxyItemize}
\begin{DoxyItemize}
\item Call the relevant get\+\_\+$<$entity$>$\+\_\+default\+\_\+qos() method. \item Modify the QoS values as desired. \item Finally, create the entity. \end{DoxyItemize}
Each {\ttfamily Qos\+Policy} is treated independently from the others. This approach has the advantage of being very extensible. However, there may be cases where several policies are in conflict. Consistency checking is performed each time the policies are modified via the \doxysectlink{dds_cpp_infrastructure.hxx_Entity_set_qos}{set\+\_\+qos (abstract)}{2} operation, or when the \doxylink{classDDSEntity}{DDSEntity} is created. 

When a policy is changed after being set to a given value, it is not required that the new value be applied instantaneously; RTI Connext DDS Micro is allowed to apply it after a transition phase. In addition, some {\ttfamily Qos\+Policy} have immutable semantics, meaning that they can only be specified either at \doxylink{classDDSEntity}{DDSEntity} creation time or else prior to calling the \doxylink{classDDSEntity_ac8f6cb9f8f0d2eac1daed34b6eb60e11}{DDSEntity\+::enable} operation on the entity. 

Each \doxylink{classDDSEntity}{DDSEntity} can be configured with a list of {\ttfamily Qos\+Policy} objects. However, not all Qos\+Policies are supported by each \doxylink{classDDSEntity}{DDSEntity}. For instance, a \doxylink{classDDSDomainParticipant}{DDSDomain\+Participant} supports a different set of Qos\+Policies than a \doxylink{classDDSTopic}{DDSTopic} or a \doxylink{classDDSPublisher}{DDSPublisher}. \hypertarget{dds_c_infrastructure.h_DDSQosTypesModule_compatibility}{}\doxysubsubsubsubsection{\texorpdfstring{QoS compatibility}{QoS compatibility}}\label{dds_c_infrastructure.h_DDSQosTypesModule_compatibility}
In several cases, for communications to occur properly or efficiently, a Qos\+Policy on the publisher side must be compatible with a corresponding policy on the subscriber side. For example, if a \doxylink{classDDSSubscriber}{DDSSubscriber} requests to receive data reliably while the corresponding \doxylink{classDDSPublisher}{DDSPublisher} defines a best-\/effort policy, communication will not happen as requested. 

To address this issue and maintain the desirable decoupling of publication and subscription as much as possible, the Qos\+Policy specification follows the {\bfseries{subscriber-\/requested, publisher-\/offered pattern}}. 

In this pattern, the subscriber side can specify a "{}requested"{} value for a particular {\ttfamily Qos\+Policy}. The publisher side specifies an "{}offered"{} value for that {\ttfamily Qos\+Policy}. RTI Connext DDS Micro will then determine whether the value requested by the subscriber side is compatible with what is offered by the publisher side. If the two policies are compatible, then communication will be established. If the two policies are not compatible, RTI Connext DDS Micro will not establish communications between the two \doxylink{classDDSEntity}{DDSEntity} objects and will record this fact by means of the \doxylink{group__DDSStatusTypesModule_ggaa99b5585ecdf8c5f93ac3108439ad26fa1eb2a68f0c66c314784737a7728922b8}{DDS\+\_\+\+OFFERED\+\_\+\+INCOMPATIBLE\+\_\+\+QOS\+\_\+\+STATUS} on the publisher end and \doxylink{group__DDSStatusTypesModule_ggaa99b5585ecdf8c5f93ac3108439ad26fa126ff1b38cdfc905353cb2dac57b6796}{DDS\+\_\+\+REQUESTED\+\_\+\+INCOMPATIBLE\+\_\+\+QOS\+\_\+\+STATUS} on the subscriber end. The application can detect this fact by means of a \doxylink{classDDSListener}{DDSListener}.
